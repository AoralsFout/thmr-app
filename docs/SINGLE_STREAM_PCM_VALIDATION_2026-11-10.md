# 单连接、共享 PCM、提前分析与播放时钟同步：实测验证

后续已完成正式宿主和 TUI 接入及前后复测，见 [正式替换报告](SHARED_AUDIO_REPLACEMENT_2026-11-10.md)。本文件保留原型验证时点的结果。

**结论：方案可行，已在当前 Windows/libmpv 环境下用真实直播跑通。** 三轮正式验证累计采集 220.907 秒音频，得到 83 个可靠波形匹配片段。每轮只有一个上游请求；同一份解码后的 PCM 同时用于播放和提前分析，指标按实际播放位置选用并回收。暂停和一次足以耗尽缓存的接收停顿没有留下持续偏移。

这是一份隔离原型的验证结果，尚未把实现接入正式 `thmrd`、TUI 客户端协议或发布包。生产源码、正常宿主和用户设置未修改。

## 原型实际做了什么

```text
一个真实 MP3 请求
    → 现有 minimp3 解码器：解码一次
    → 同一份 float PCM
        ├─ 有界 PCM 队列 → libmpv 自定义输入流 → 实际系统音频输出
        └─ 现有 FFT/音乐指标分析器 → 带累计样本位置的指标队列

libmpv audio-pts → 当前播放样本位置
    → 取出已经到期的指标 → 原有 Ui.tick / 舞台渲染
    → 回收已取出的指标
```

- libmpv 输入使用 `mpv_stream_cb_add_ro`，由内存队列提供 raw float PCM；播放端不会再次请求电台，也不再解码 MP3。当前 DLL 实测为 `mpv v0.36.0-403-g652a1dd907`，调用及结构按该版本的 [stream callback 接口](https://github.com/mpv-player/mpv/blob/v0.36.0/libmpv/stream_cb.h)实现。
- raw PCM 起点就是共享样本时间轴的零点，指标使用累计样本数；由 `audio-pts × 输入采样率` 映射播放位置。`audio-pts` 的定义包含音频驱动延迟，见 [mpv 播放位置文档](https://mpv.io/manual/master/#property-list)。最终同步仍通过 WASAPI 输出波形校验，而不只相信该属性。
- 分析拿到缓存 PCM 后立即计算，没有独立的逐帧 sleep。提前生成的指标留在队列里，不提前推给舞台。
- 分析领先量限制为约 3 秒，允许最多一个 MP3 帧的越界。达到上限便停止继续消费上游数据，等待播放推进；队列不是按运行时长增长。
- 播放端从 PCM 队列读走数据后释放相应应用队列字节；播放器内部缓存会继续持有尚未播放的数据。指标在播放游标经过后弹出。日志/录音为验证证据，另行写盘，不属于运行队列。
- 原型保留与当前项目相同的 2048 点 FFT、1024 样本 hop、音乐特征、舞台状态与终端渲染。它把宿主和舞台放在同一验证进程里，没有测量将来跨进程传递指标的开销。

## 真实直播结果

所有时差均为正数，即指标/帧略晚于系统音频输出。内容位置仍按 FFT 窗口末端定义，与此前双连接报告保持一致。

| 测量 | 有效片段 | 指标被选用时差：中位数 / P95 | 舞台帧提交时差：中位数 / P95 | 分析提前量中位数 |
| --- | ---: | ---: | ---: | ---: |
| 音源 1，正常播放 75 s | 27 | 8.1 / 27.9 ms | 20.2 / 129.4 ms | 1333 ms |
| 音源 1，暂停与接收停顿，80 s | 24 | 8.1 / 21.6 ms | 15.8 / 41.8 ms | 2994 ms |
| 音源 2，独立启动 75 s | 32 | 11.3 / 22.5 ms | 18.5 / 78.1 ms | 610 ms |

三个指标选用时差中位数都在 8–12 ms 内，没有此前 −814、+135、−817 ms 的大幅偏移及方向变化。该结果是三个连接的样本，不是正式产品的性能保证，也不是严格控制网络条件的 A/B 基准。

“指标被选用”与“舞台帧提交”分别计时：前者在读取播放位置并选定对应特征时记录；后者在真实 `terminal.draw` 完成后记录。第一轮出现过约 171 ms 的帧提交异常值，而指标选用 P95 仍约 28 ms，说明终端绘制/提交的慢帧仍可能增加可见响应延迟；共享音频时钟不会自动解决渲染卡顿。

两路源音频都是 44.1 kHz、双声道，系统采集为 48 kHz。83 个有效片段之外另有 13 个候选片段因波形匹配不明确或采集时间不连续被排除。三轮相关系数中位数分别约 0.98751、0.99745、0.999999。没有把排除的片段当作同步成功。

## 暂停、停顿恢复和回收验证

第二轮主动执行了两种情况：

1. **第 20–22 秒暂停播放器。** 共记录 50 个暂停状态采样。指标游标变化为 0，已回收指标计数变化也为 0；提前计算的指标留在队列中，等待恢复播放。
2. **约第 37 秒停止消费网络数据 6 秒。** 这是客户端接收停顿注入，服务器连接保持打开；不是服务器故障或完整重连。已有播放缓冲确实耗尽，注入之后记录到 108 个 `paused-for-cache` 状态采样。恢复后继续按真实播放时钟取指标。

注入停顿前，波形对齐的指标选用时差中位数为 **6.33 ms**；恢复并稳定后为 **8.76 ms**，变化约 **2.43 ms**。因此本次停顿没有像原来的独立分析时钟那样，留下几百毫秒或一秒的持续偏移。

第二轮应用队列情况：

- 分析领先峰值约 **3.026 s**，符合 3 秒加一个 MP3 帧的限制。
- 指标队列峰值 **119 条**，累计回收 **2756 条**，退出时剩余 **115 条**尚未到期指标。
- 应用 PCM 队列峰值 **571392 字节**，约 **0.545 MiB**。这个数字不包括 libmpv 内部缓存、网络栈和写盘证据。
- 三轮分别累计回收 2760、2756、2785 条指标；没有选取时间戳超前于播放器当前位置的指标，也没有回收计数倒退。

上述条件由分析命令实际检查，包括上游请求数为 1、队列领先量 <3.1 秒、指标提前计算、暂停时游标冻结、注入确实触发缓冲，以及恢复前后持续偏移变化 <75 ms。最后一项的本次实测值为 2.43 ms；75 ms 是原型检查阈值，不是产品承诺。

## 已验证与尚未验证的范围

已验证的是当前 Windows/libmpv 上“一条上游连接、一次解码、同源 PCM、提前分析、播放时钟取指标、有界缓存与消费回收”的技术路线，包含一次保留当前流的暂停恢复和一次接收停顿后的重新缓冲。

正式接入仍需处理宿主与 TUI 间带时间戳的指标传输、跨进程时钟映射、断开连接后的代次切换、来源切换、采样格式变化、长期运行和其他平台。原型遇到采样格式变化会明确失败，不会偷偷把新格式接在旧时间轴上。本次分别独立启动了两个音源，未验证运行中切换音源或自动重连。

当前产品的暂停语义是停止下载、恢复时加入直播边缘；本次实验的暂停保留当前连接和内容。正式实现应按现有语义建立新代次并丢弃旧指标，不能直接照搬实验的保留流暂停。

保持播放/分析同步也不代表降低了播放相对广播源的总延迟。原型为了验证有界提前分析，允许上游消费受 3 秒领先量限制；这与追赶直播边缘是两个问题。

测量仍止于 WASAPI 输出端点和终端提交，不包含屏幕扫描、设备无线传输或声学路径。若按 FFT 窗口中心定义内容位置，各项时差再加约 23.22 ms。长测的前 10 秒未用于定量波形统计，因此不据此承诺首帧延迟。
